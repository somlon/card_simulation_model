# 엔진 상태 모델 — 초안

설계 문서다. 코드는 쓰지 않는다. 기준은 룰지 **0장**(아홉 개의 존)과 **3장**(턴의 다섯 단계)이고,
`docs/맵_형식.md` 4장이 뽑은 술어 목록이 이 상태 위에서 실제로 계산 가능한지를 검증하는 것이 이 문서의
두 번째 목적이다. `docs/목표_수준.md` 4장(엔진 속도가 4단계의 전제조건)을 설계 전제로 삼는다 — "일단
돌아가게 만들고 나중에 최적화"가 아니라 **상태 복제 비용과 합법수 생성을 핫 패스로 보고 처음부터 그 모양으로
설계**한다.

## 0. 설계 원칙

- 이 문서는 **자료구조의 모양**을 정한다. 알고리즘(탐색 · belief · CFR)은 2~4단계의 몫이고 여기서 다루지 않는다
- `rules/충돌목록.md`의 미해결 2건(체인 처리 순서 G1 · 뒷면 마법 특수 케이스)과 `진행.md`의 "릴리스" 미정의는
  **이 설계가 사용자 판정을 기다리는 동안도 막히지 않도록** 인터페이스를 비워 두는 방식으로 흡수한다(4 · 5장).
  임의로 하나를 골라 박아 넣지 않는다
- 카드 텍스트(`data/card_pool.json`)는 **읽기 전용 정적 테이블**로 두고, 게임이 진행되며 바뀌는 것(존 위치 ·
  카운터 · 사용 횟수 등)만 "상태"로 둔다. 이 구분이 3장 전체의 전제다

## 1. 아홉 개의 존 + 패 — 상태로 옮기기

룰지 0-1~0-9가 "아홉 개의 존"이라고 부르는 것은 유닛 존 · 이펙트 존처럼 5칸인 것도 한 종류로 센 것이다
(`뉴_네오_룰지_2026-10-23.txt:58, 94~116`). 플레이어별로 옮기면:

| 존 | 수 | 소유 | 가시성 | 저장 방식 제안 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 메인 덱 (0-1) | 1 | 자신 | 비공개(순서 · 내용) | 카드 ID 리스트 (순서 유지) | 매수는 공개 정보(상대도 셀 수 있음), 내용은 비공개 |
| 상급 덱 (0-2) | 1 | 자신 | 비공개 | 카드 ID 리스트 | 위와 동일. `상급덱잔량()` 술어가 바로 이 리스트 길이 |
| 아카이브 (0-3) | 1 | 자신 | **공개**(양쪽 다 봄) | 카드 ID 리스트 (쌓인 순서 유지할 필요는 없으나 내용 전부 열람 가능해야 함) | 묘지 축적형 장부(던전마스터 1-2 "종류 수")가 이 리스트를 집합으로 센다 — 카운트만으론 안 됨, **식별 가능한 리스트**로 둬야 함 |
| 공허 (0-9) | 1 | 자신 | 공개 | 카드 ID 리스트 | 아카이브와 별도 존. 구조는 동일 |
| 유닛 존 (0-4) | 5 칸 | 자신 | 공개(앞면 한정) | 고정 크기 배열 `[5]`, 빈 칸은 `None` | 칸 번호 자체는 의미가 없다(이동 규칙 없음) — 다만 **슬롯 식별자**는 "이 유닛을 가리키는 효과"의 대상 해석에 필요 |
| 이펙트 존 (0-6) | 5 칸 | 자신 | 조건부(로드=뒷면 비공개, 발동/지속=앞면 공개) | 고정 크기 배열 `[5]` | 뒷면 로드 카드는 "식별자는 아는데 텍스트는 비공개"가 아니라 **진짜 정체 자체가 숨김** — 7장 정보 상태와 연결 |
| 필드 존 (0-7) | **1, 양쪽 공유** | 어느 한쪽(발동한 플레이어) | 공개 | 단일 슬롯 (플레이어 합산이 아니라 **테이블 전체에 하나**) | "필드 존은 양쪽 플레이어가 공유한다"(`:111`) — 호박옥 덱요약이 암묵적으로 "자신 필드 카드"처럼 쓰는 곳이 있다면 이 단일성과 충돌할 수 있어 점검 필요 |
| 공유 존 (0-5) | **1, 양쪽 공유** | 마커로 가변 | 공개 | 단일 슬롯 + 소유 마커 필드 | 마커 뒤집힘 시 세 가지 페널티(`:105~108`) 처리를 상태 전이의 일부로 모델링 |
| 스킬 존 (0-8) | 1 | 자신 | 항상 공개 | 고정 슬롯, 불변 | 파괴·이탈 불가. 무효화되어도 종료 시 재활성화(`:192`) — "무효 상태" 플래그만 턴마다 리셋하면 됨, 카드 자체는 안 움직임 |
| **패 (비공식)** | 1 | 자신 | 비공개(매수는 공개) | 카드 ID 리스트 | **0장이 나열하는 아홉 개 안에 패가 없다.** 공식적으로는 "존"이 아니지만 소환 · 발동의 출처로 실제 상태에는 반드시 있어야 한다 — 설계가 "9개 존"에만 집중하면 빠뜨리기 쉬운 지점이라 명시해 둔다 |

### 1-1. 설계에 바로 영향을 주는 것

- **매수(count)와 식별자 리스트를 구분한다.** 상대에게 비공개인 존(메인 덱 · 상급 덱 · 패 · 로드된 이펙트
  카드)은 "몇 장인가"는 공개 정보이고 "무엇인가"는 비공개다. 상태 모델이 둘을 같은 자료구조에 섞으면
  belief 계산(2층)이 "진짜 상태"와 "공개된 정보"를 분리하지 못하게 된다 — 7장에서 다시 다룬다
- **필드 존 · 공유 존은 플레이어별 슬롯이 아니라 테이블 전체에 하나뿐이다.** 플레이어 상태를 단순히
  두 개 복제해서 합치는 구조로 설계하면 이 두 존이 중복 생성되는 버그가 난다 — 전체 상태(GameState)에
  필드 존 · 공유 존을 **한 번만** 두고, 플레이어별 상태(PlayerState)에는 나머지(덱 · 패 · 유닛 존 ·
  이펙트 존 · 아카이브 · 공허 · 스킬 존)를 둔다

## 2. 카드 인스턴스 표현

### 2-1. 정적 데이터와 동적 상태를 분리한다

`card_pool.json`의 한 레코드(이름 · 레벨 · 공수 · 텍스트 · 태그 등)는 게임 중 바뀌지 않는다(바뀌는 것처럼
보이는 "뒷면이 되면 효과가 사라진다" 류는 **상태 쪽의 "무효" 플래그**로 표현되지, 정적 데이터를 고치는 게
아니다). 그래서:

```
정적 테이블 CardDef[card_id] = { name, level, atk, def, text, tags, groups, color, deck(메인/상급), type, race, attr, ... }
  — 전체 게임에서 한 번만 로드, 읽기 전용, 모든 State가 공유 (참조만 함)

동적 인스턴스 CardInstance = {
  card_id,                 # CardDef를 가리키는 정수 ID (텍스트 복사 금지 — 속도, 9장 참조)
  zone, owner, slot,       # 지금 어디에 있는가
  facing,                  # 앞면 / 뒷면
  orientation,             # 공격 표시 / 수비 표시 (유닛에만 의미)
  counters: {counter_name: int},   # 6장
  turn_flags: {소환됨, 효과소환됨, 표시변경사용함, 공격선언함, 로드한턴, ...},  # 이번 턴 한정, 매 턴 리셋
  effect_use_count: {effect_index: int},  # 1턴1번 카운터 (1장 "전역 규칙")
  negated_until,           # 효과로 무효화된 경우 해제 시점
}
```

- **왜 ID 참조인가** — 카드 텍스트 · 태그 문자열을 인스턴스마다 복사하면 상태 복제(탐색의 매 분기)마다
  문자열 복사 비용이 들어간다. 정적 테이블은 변하지 않으므로 포인터/인덱스 하나로 충분하다
- `counters`는 이름별 딕셔너리로 뒀지만, 이 게임에 등장하는 카운터 이름의 종류는 적다(봉인 · 퇴마 ·
  …) — 엔진 착수 시 전체 카드 풀에서 카운터 이름을 전수 추출해 **정수 enum**으로 바꾸고 딕셔너리 대신
  고정 크기 배열로 두면 해시 비용 없이 접근할 수 있다. 지금은 이름 공간이 확정되지 않았으니 딕셔너리로
  설계해 두고, 엔진 착수 시 이 최적화를 적용한다

### 2-2. "뒷면이 되면 처음 상태로 돌아간다"의 처리

룰지 1-1(`:169`) — "뒷면이 되었다가 다시 앞면이 된 유닛은 처음 상태가 된다. 카운터, 공격력 · 수비력의
변화, 받은 효과, 무효는 모두 사라진다." 이것은 인스턴스를 수정하는 게 아니라 **그 자리의 CardInstance를
통째로 새로 만들고 counters · turn_flags · negated_until 등을 초기값으로 리셋**하는 것으로 모델링한다.
"뒷면 → 앞면"을 하나의 전이로 보고, 그 전이 함수가 위 필드들을 일괄 초기화하도록 못 박아 둔다 — 필드를
하나씩 수동으로 지우다 빠뜨리는 버그를 막는다.

## 3. 턴 상태 — 5단계와 사용 횟수

### 3-1. 단계 열거 (3장)

```
준비(드로우) → 진행(소환·발동·로드) → 전투(공격 선언) → 정비(효과소환·로드) → 종료(a·b·c·d)
```

(`:211~314`). 종료 단계는 하위 네 단계가 더 있다 — a(턴 종료 시 효과 처리) → b(패 7장 상한) →
c(턴 종료까지 적용 효과 무효화) → d(턴 넘김). **a에서 발동된 효과가 체인을 이루면(예: 태고의 수해 +1과
스킬 세금 −2가 같은 타이밍) 4장의 체인 모델을 거쳐야 하므로, a 자체가 하나의 "단계"가 아니라 그 안에
우선권 교환이 또 들어간다** — 단계 enum은 `(phase, sub_step)` 두 겹으로 둔다.

### 3-2. 단계별 허용 행동 — 5장 키워드 매트릭스

| 키워드/행동 | 자신 턴 | 상대 턴 | 근거 |
| --- | --- | --- | --- |
| 소환 (일반) | 진행 단계만 | 불가 | `:230~243` "할 수 있는 때 — 자신의 진행 단계" |
| 효과 소환 | "효과를 쓸 수 있는 때 언제나" | 효과에 따라 가능 | `:243` |
| 이펙트 카드 — 일반 | 자신 턴만 | 불가 | `:175` |
| 이펙트 카드 — 신속 | 가능(로드한 턴 당일 제외) | 가능(로드 필요) | `:176~177` |
| 이펙트 카드 — 트리거 | 조건 충족 시 양쪽 | 조건 충족 시 양쪽 | `:178~179` |
| 이펙트 카드 — 지속 | 발동 즉시부터 계속, 별도 선언 없음 | 동일 | `:368~369` |
| 로드 | 진행 · 정비 단계만 | — | `:184` |
| 표시 형식 변경 | 유닛당 1턴 1번, 그 턴 소환/효과소환된 유닛은 불가 | (상대 유닛에는 못 함) | `:165` |
| 공격 선언 | 전투 단계, 유닛당 1회 | — | `:274~276` |

→ **몬스터 효과 · 스킬 효과처럼 "키워드가 없는" 효과의 기본 타이밍은 룰지가 직접 말하지 않는다.**
`maps/던전마스터_셔플.md` 4-1이 이미 짚은 공백이다 — 이 표의 "소환 (일반)" 행과 같은 제약(자신 턴
한정)을 유닛/스킬 효과 전반의 기본값으로 **가정**하되, 신속이 없으면 상대 턴에 못 쓴다는 것만 확정 사실로
싣는다. 상태 모델의 "행동 가능 여부 판정" 함수는 이 표를 하드코딩하지 않고 **키워드 집합 → 타이밍 규칙**의
룩업으로 두어, 표에 새 행이 추가되어도(예: 4-2의 신속 1턴1번 범위가 확정되면) 로직을 다시 안 짜도 되게 한다

### 3-3. 1턴 1번 — 리셋 시점

1장 전역 규칙("모든 효과는 1턴에 1번", `:121`)의 "턴"은 3-6 턴 정의상 **한 플레이어의 5단계 묶음**이다
(`maps/던전마스터_셔플.md` 4-2가 이미 이 정의를 근거로 "자신 턴 · 상대 턴이 각각 다른 턴"이라는 해석을
제기했지만 재정 확인이 없어 미해결이다). 상태 모델은 이 미해결을 다음처럼 흡수한다:

```
effect_use_count 리셋 시점 = "턴이 끝날 때" (자신 턴 종료 d단계가 끝나는 순간)
→ 자신 턴에 쓴 사용 횟수는 자신 턴이 끝나면 0으로 리셋된다.
→ 상대 턴에 쓴 사용 횟수(신속 등)는 그 상대 턴이 끝날 때 리셋된다.
```

이 리셋 모델은 "자신 턴 몫·상대 턴 몫이 따로 있다"(라운드당 최대 2회) 해석과 **이미 호환된다** —
사용 카운터가 턴마다(내 턴이든 상대 턴이든) 리셋되므로, 자연히 각 턴에 1번씩 쓸 수 있다. 반대로
"라운드당 1회"로 확정되면, 리셋 시점을 "자신 턴이 시작할 때만"으로 좁히는 수정 한 줄로 바뀐다. **즉
이 설계는 4-2 미해결의 어느 결론이 나와도 구조를 바꾸지 않고 리셋 조건 하나만 바꾸면 된다** — 설계가
미해결 때문에 막히지 않는다.

## 4. 체인 · 우선권 — G1을 설계에 흡수하는 법

**G1 결정됨 (2026-10-25, 사용자 — `rules/충돌목록.md` 「판정」절, 커밋 `cb9deab`).** 아래 두 후보
중 **`resolve_order_A`로 고정한다** — 룰지 3-6 b 대로 턴 플레이어가 먼저 처리. 재정 G1(`resolve_order_B`,
LIFO)은 참고로만 남긴다. 이 문서의 나머지는 결정 전에 쓴 흡수 설계라 그대로 두되(왜 두 함수로
나눴는지의 근거이자, 41회차가 `engine/legalmoves.py`에서 "G1 미해결"을 잘못 반복한 것을 바로잡을
때 이 결정을 다시 확인한 기록이다), **구현 시점에는 아래 `resolve_order_B` 분기를 만들 필요가
없다 — 처음부터 A 하나만 구현한다.**

### 4-1. 모델

```
PendingEffect { source_card_instance, effect_index, controller }
체인 = PendingEffect의 리스트 (선언된 순서)

declare_order(state) -> 리스트       # "누가 먼저 선언하는가" — 턴 플레이어 우선 (룰지 3-6 b, 충돌 없음)
resolve_order(체인) -> 리스트         # "선언된 것을 어떤 순서로 처리하는가" — 여기가 G1 쟁점
```

룰지 3-6 b의 "선언"과 "처리" 두 동사를 상태 모델에서도 **별도 함수**로 분리해 둔다. 선언 순서는 재정과
룰지가 일치하므로(턴 플레이어 우선) 바로 구현해도 된다. 처리 순서만 두 가지 후보를 둔다:

```
resolve_order_A (룰지 3-6 b 숫자 예시 그대로) — 선언 순서와 같은 방향. 턴 플레이어가 먼저 처리된다.
resolve_order_B (재정 G1)              — 선언 역순(LIFO). 상대가 먼저 처리되고 턴 플레이어가 마지막.
```

상태 모델은 `resolve_order`를 **설정 가능한 함수 하나**로 노출한다. 사용자가 G1을 확정하면 이 함수
하나를 고정하면 끝나고, 엔진의 나머지(체인 적재 · 무효 처리 · [트리거]/[소환]/[유언]의 "우선 선언" 규칙
`:321` 등)는 손댈 필요가 없다. **지금 둘 중 하나를 임의로 골라 구현하면 안 되는 이유가 여기 있다** —
무효화 체인(황금봉랍 · 다크 매지션 등 양쪽 다 상대 턴 반응 카드가 많은 구조)에서 두 모델의 승부 결과가
갈릴 수 있는데, 코드에 하나를 박아 두면 나중에 뒤집을 때 그 가정 위에 쌓인 다른 로직(belief 모델이
"상대가 먼저 반응했다"는 전제로 학습한 통계 등)까지 다시 손봐야 한다.

### 4-2. 뒷면 마법 특수 케이스(충돌 2)도 같은 식으로 둔다

"뒷면 로드된 마법(트랩)이 제거 효과의 대상이 될 수 있는가"는 룰지 1-1의 일반 조항이 **유닛 전용인지
전체 카드 조항인지**에 달려 있다(`rules/충돌목록.md` #2). 대상 지정 가능 여부를 묻는 함수를 설계할 때

```
is_targetable(card_instance) -> bool
```

을 "카드 종류(유닛/이펙트)"와 "뒷면 여부"를 둘 다 인자로 받는 룩업으로 두고, 지금은 **룰지 1-1을 그대로
전체 카드에 적용**(뒷면이면 유닛 · 이펙트 종류를 안 가리고 불가)하는 보수적 기본값을 쓴다. 재정의 예외
(뒷면 마법 + 제거 계열만 허용)는 `is_targetable`의 분기 하나를 추가하는 선에서 끝나도록, 효과의 "계열"
(제거 vs 기타)을 애초에 효과 메타데이터에 태그해 둔다 — 결정이 나기 전까지는 이 태그를 참조하지 않는
쪽(보수적 기본값)으로 꺼 둔다.

## 5. "릴리스" 미정의 — 추상 행동으로 분리

`진행.md` 미해결 — "릴리스"가 부록 B에 없고, 계승(아카이브로 보내는 것)과 같은 동작인지 확정 근거가
없다. 카드 풀 거의 전체가 쓰는 동사라 엔진의 액션 타입 설계에 직접 영향을 준다. 상태 모델은 이것을
**계승과 다른 이름의 별개 액션 타입**으로 둔다:

```
Action.계승(카드)   — 룰지 3-2 정의: 효과가 아님(:267), 처리 계승 시 아카이브로 보냄, "계승할 수 없다" 카드는 불가
Action.릴리스(카드) — 정의 보류. 계승과 같은 틀(자신 필드 카드를 코스트로 아카이브로 보냄)을 임시로 빌리되,
                      "효과인가 아닌가"(내성이 막는지), "[유언]을 발동시키는가"는 별도 플래그로 열어 둔다
```

계승은 룰지가 "효과가 아니다"(`:267`), "파괴가 아니다"(`:268`)라고 명시했지만 릴리스는 그런 명문 규정이
없다. 두 액션을 처음부터 같은 함수로 합치면, 나중에 "릴리스는 효과다"로 확정될 경우 계승까지 같이 영향
받는 코드가 생길 위험이 있다 — 이름이 다른 별개 액션으로 둬서 그 위험을 미리 끊는다. 결정이 나오면
`릴리스`의 플래그 값만 채우면 된다.

## 7. 정보 상태 — belief(2층)를 위한 분리

이 항목은 룰지 0 · 3장에 직접 나오지 않지만, 4단계(CFR)와 2층(belief) 설계가 요구하는 축이라 상태 모델
단계에서 자리를 미리 비워 둔다.

```
GroundTruthState   — 실제 게임 상태. 모든 카드의 진짜 정체 · 위치 · 카운터를 포함 (시뮬레이션은 이것으로 돈다)
InformationView(player) — 그 플레이어가 "안다고 할 수 있는" 부분만 담긴 투영
  = GroundTruthState에서 상대 비공개 존(패 · 메인/상급 덱 내용 · 상대가 로드한 뒷면 이펙트 · 뒷면 유닛의 정체)을 지운 것
  + 공개된 매수 정보(패 매수, 덱 잔량)
  + "누가 무엇을 봤는가"의 이력(관찰 로그) — 셸 게임형 정보 작전(던전마스터 Y노드)이 성립하려면 이 이력이 필요
```

- CFR·belief는 `GroundTruthState`로 게임을 돌리면서 각 플레이어에게는 `InformationView`만 들려준다 —
  이 분리가 없으면 "복기는 그 시점의 belief로만 평가한다"(`docs/목표_수준.md` 3장, 사후편향 금지)는
  규칙 자체를 지킬 수 없다. 사후편향 금지는 **InformationView가 GroundTruthState의 미래 정보를
  새지 않는 것**을 전제로 하기 때문이다
- 던전마스터 Y노드(재배치 때 행위자가 뒷면 카드 정체를 보는가, `진행.md` 미해결)는 정확히 이 투영
  함수의 분기다 — "나만 아는 셸 게임"이면 재배치를 실행한 플레이어의 `InformationView`에는 정체가
  남고 상대에게만 지워진다. "양쪽 다 모르는 불완전정보"면 재배치 행위 자체가 `GroundTruthState`
  안에서도 "무작위 치환"으로 처리되어 **행위자의 InformationView에도 지워진다.** 두 가지 투영 방식
  차이이지, GroundTruthState의 자료구조 자체는 바뀌지 않는다 — 이 미해결이 풀리기 전에도 상태 모델은
  설계를 바꿀 필요가 없다는 뜻이고, 2층 설계 때 투영 함수의 분기 하나만 결정하면 된다

## 8. `docs/맵_형식.md` 4장 술어 검증

4장이 호박옥 맵에서 뽑은 1차 술어 집합이 이 상태 모델 위에서 계산되는지 표로 확인한다.

| 술어 | 계산 가능? | 상태 모델의 어떤 필드를 쓰는가 | 비고 · 갭 |
| --- | --- | --- | --- |
| `잔고()` | 가능 | 자신 유닛 존의 모든 CardInstance.counters["봉인"] 합 | 카운터 이름을 문자열로 거는 한 덱마다 다른 이름이라 맵 쪽에서 이름을 넘겨야 함 — `잔고(카운터명)`으로 일반화하는 편이 나음 |

| `상대앞면유닛수()` | 가능 | 상대 유닛 존 5칸 중 facing==앞면 개수 | 직접 |
| `상대HP()`, `내HP()` | 가능 | PlayerState.hp | 직접 |
| `상급덱잔량()` | 가능 | PlayerState.상급덱 리스트 길이 | 1-1에서 이미 확정한 "매수만 공개" 설계와 맞음 |
| `리설가능(타격합)` | 가능 | `타격합 >= 상대HP()` | `타격합` 자체는 맵이 공격 가능한 유닛들의 ATK를 모아 계산 — 엔진은 "공격 가능 여부"(아래)만 제공 |
| `직접공격가능()` | 가능 | `상대앞면유닛수() == 0` (룰지 3-3, `:277` "뒷면만 있을 때도 가능") | 직접 |
| `표시변경가능(유닛)` | 가능, **턴 플래그 필요** | `유닛.turn_flags.표시변경사용함 == False and 유닛.turn_flags.소환됨 == False` | 1-1(`:165`)의 두 조건이 그대로 턴 플래그로 매핑됨 — 2장에서 이미 설계에 포함 |
| `대상지정효과인가(카드)` | 가능, **정적 전처리 필요(갭)** | CardDef.text에 "대상으로 하고 발동" 포함 여부 | `card_pool.json`에 이 구분을 담는 필드가 없다(태그 · 그룹 모두 테마용). 매번 텍스트를 정규식으로 긁으면 핫 패스에서 느리다 — 카드 로드 시점에 한 번만 파싱해 CardDef에 `targets_specifically: bool`로 캐시해 두는 **정적 전처리 단계**가 필요하다. 재정 6차 Q2(「대상으로 하고 발동」=대상, 「고르고」=비대상, 호박옥 맵 7-2)를 전처리 규칙으로 그대로 쓸 수 있다 |
| `세금재원있음(제외할유닛)` | 가능 | 자신 유닛 존 중 `제외할유닛`이 아닌 것들의 카운터 합 ≥ 세금액 | 직접 |

**결론 — 1차 술어 집합 전부가 이 상태 모델 위에서 계산된다.** 갭은 두 개뿐이고 둘 다 "상태를 못
읽는다"가 아니라 "카드 텍스트를 미리 구조화해 두지 않았다"는 **정적 데이터 전처리 문제**다 — 상태
모델의 모양을 바꿀 필요는 없다.

### 8-2. 2장에 반영한 수정

## 9. 속도 설계 원칙 (`docs/목표_수준.md` 4장 반영)

CFR류는 수천만 국면을 돈다. 이 문서의 자료구조 선택은 전부 아래 네 가지를 겨냥한 것이다:

1. **상태 복제 비용 최소화** — 카드 텍스트 · 태그를 인스턴스마다 들고 있지 않고 정적 테이블 ID 참조로만
   둔다(2-1). 상태를 복제할 때 움직이는 바이트 수가 줄어든다
2. **고정 크기 배열** — 유닛 존 · 이펙트 존은 5칸을 못 넘으므로 가변 리스트가 아니라 고정 크기 배열로
   둔다(1장). 메인 덱 · 패처럼 크기가 변하는 것만 리스트로 둔다
3. **되돌리기(undo) 가능한 수 적용을 전제로 둔다** — 탐색(CFR · minimax)은 같은 상태에서 가지를 치며
   앞으로 갔다 되돌아오는 동작이 압도적으로 많다. 매 수마다 전체 상태를 깊은 복사하는 대신, "이 수가
   건드린 필드와 이전 값"만 담은 되돌리기 레코드를 만들어 적용/역적용하는 모델을 쓴다 — 이 문서의 모든
   전이(계승 · 릴리스 · 카운터 변화 · 뒷면 전환)가 "이전 값 → 새 값" 한 줄로 적힌 것은 이 되돌리기
   레코드를 그대로 만들 수 있게 하기 위함이다
4. **합법수 생성은 핫 패스다** — 3-2의 "단계별 허용 행동" 룩업처럼, 행동 가능 여부 판정을 카드마다
   분기 조건을 새로 짜는 대신 **키워드 집합 → 규칙**의 일반화된 질의로 둔다. 질의 자체가 CardDef의
   사전 계산된 필드(8장의 `targets_specifically` 같은 것)를 참조하게 해서, 매 분기마다 텍스트를 다시
   읽지 않게 한다

이 네 가지는 전부 **설계의 모양**이고, 실제 벤치마크(초당 시뮬레이션 수 측정)는 엔진 착수(코드 작성)
시점에 벤치마크 스크립트와 함께 만든다(`docs/목표_수준.md` 4장 "초안 단계에서 측정 가능한 형태로 둔다").
